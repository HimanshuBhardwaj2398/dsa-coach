Intervals, explained

Sort the intervals, then sweep once. After sorting by start, an interval can only overlap the ones just before it, so one comparison with the last kept interval decides each step.

Spot it

Interval problems (meetings, ranges, bookings, balloons) ask how intervals overlap. Unsorted, any interval might overlap any other: n² pairs. Sorted by start, an interval that doesn't overlap the last merged one can't overlap anything earlier either, so one sweep with one comparison per interval is enough.

What you sort by depends on the question. By start to merge or insert. By end to keep the most non-overlapping intervals (the one that ends first leaves the most room: a greedy exchange argument). For how many at once, sort the starts and keep a min-heap of end times, or sweep +1/−1 events.

Ask yourself

  1. When do two intervals overlap? a.start <= b.end and b.start <= a.end. Check whether touching ends count.
  2. What should they be sorted by? Start for merging; end for keeping the most; both event lists for counting.
  3. Whom do I compare with? The last kept interval, not the previous one in the input.
  4. Do I need how many overlap at a moment? A heap of end times, or a sweep of +1 at starts and −1 at ends.

Looks like it, isn't

  • Range sum queries. Ranges over an array: prefix sums, not interval sweeps.
  • Activities with weights (maximize total weight). Sorting by end isn't enough: weighted interval scheduling is DP with binary search.
  • Overlapping windows of a string. Sliding window: the window moves over the input, it isn't an input interval.

What stays true

merged is sorted and non-overlapping, and it covers exactly the intervals processed so far.

Why each move is safe

  • Every earlier merged interval ends before merged[-1] starts, and the new interval starts at or after merged[-1]'s start. So if it doesn't reach merged[-1], it reaches nothing earlier.
  • When it overlaps, the union is [merged[-1].start, max(both ends)]: max, because the new interval may end inside the last one.
  • Sorting first is what makes the previous two bullets true; without it, a later interval could reach back over several merged ones.

Relies on: sorting by start. Decide once whether intervals that only touch (end == start) overlap; LeetCode's Merge Intervals says they do.

The comparison runs once per interval: n runs at O(1). But one line runs once and costs more: sorted(intervals) is O(n log n). The decisive cost is runs × cost of one run, so the sort decides: O(n log n). The heap version does n pushes and up to n pops at O(log n) each: also O(n log n).

Where it breaks

  • Comparing with the previous input interval instead of the last merged one misses chains like [1, 10], [2, 3], [4, 5].
  • merged[-1][1] = end instead of max(...) shrinks the merged interval when the new one sits inside it.
  • Sorting by end to merge breaks the proof: an interval can then reach back over several merged ones.
  • Mixing < and <= decides whether touching intervals overlap. Read the problem: meetings [1, 5) and [5, 8) don't conflict.
