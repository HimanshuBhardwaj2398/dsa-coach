Chapter 1 · Before you start

Last in, first out

A stack lets you touch one end only: the top. You push an item onto the top, pop the top item off, peek at it without removing it, and ask whether the stack is empty. Whatever went in last comes out first.

In Python a stack is a plain list, and the top is the end of the list, stack[-1]. Drawn as a pile, the top is at the top. Written as a list, the top is on the right.

    Chapter 2 · Stage 1 · Understand

    Valid Parentheses, in your own words

    LeetCode 20. Given a string s made only of ()[]{}, return True when all three rules hold:

    1. Same type. Every opener is closed by a closer of the same type.
    2. Right order. Openers are closed in the correct order.
    3. Nothing left over. Every closer has an opener before it, and every opener gets closed.

    The constraint is 1 ≤ len(s) ≤ 10⁴, so aim for O(n) or O(n log n). Chapter 3 measures what an O(n²) idea costs at that size.

    Decide each one before you check. For the invalid ones, say which rule breaks.

    Chapter 3 · Stages 2–3 · Brute force, then count

    Delete the innermost pair, then start over

    A valid string that isn't empty always has two neighbours that form a matched pair, like (): its innermost pair. Deleting that pair keeps a valid string valid and an invalid one invalid. So keep deleting pairs. If nothing is left at the end, the string was valid.

    Brute force · Python
    def is_valid_brute(s):
    pairs = {"()", "[]", "{}"}
    while True:                         # one pass per deletion
        for i in range(len(s) - 1):     # scan from the left, every time
            if s[i:i + 2] in pairs:     # an innermost pair
                s = s[:i] + s[i + 2:]   # delete it (copies the string)
                break                   # and start over
        else:                           # a whole scan found no pair
            return s == ""              # valid iff nothing is left

    The one-liner most people try first does the same thing a layer at a time:

    def is_valid_replace(s):
    while "()" in s or "[]" in s or "{}" in s:
        s = s.replace("()", "").replace("[]", "").replace("{}", "")
    return s == ""
    Brute force, one pair check per step

    What to notice

    • Every pass starts again at index 0 and reads the same unmatched openers it read last time. Those are the grey repeat checks: the pair of characters is identical, so the answer is too.
    • Every deletion builds a new string, copying everything that's left.
    • Try Deep nesting: the openers at the front get re-read on every pass.

    Count it

    How to count any program on this page
    1. Runs. How many times does each line run in the whole program? Count all of its runs, not the runs per loop pass. Python's tracer counts this, and every lab's code panel shows it to the left of each line.
    2. Cost. What does one run of that line cost? Most lines cost O(1). A line that copies or scans costs the length it touches.
    3. Biggest term. The time is the sum of runs × cost over all lines. A program's number of lines doesn't grow with n, so the line with the biggest runs × cost decides the Big-O.

    The brute force's worst case is k openers followed by k closers, so n = 2k. Two lines decide its cost:

    linerunscost of one runruns × cost
    5if s[i:i + 2] in pairs:k + (k − 1) + … + 11k(k + 1)/2
    6s = s[:i] + s[i + 2:]k, one per deletioncopies what's left: 2k − 2, then 2k − 4, …, 0k² − k

    Every pass starts at index 0 and stops at the innermost pair, which moves one place left each time. So line 5 runs k times in the first pass, then k − 1, down to 1. Both terms grow like k² = n²/4, so the brute force is Θ(n²). The tracer agrees:

    Chapter 4 · Stages 4–5 · Repeated work, classify

    Restarting is the waste, so remember instead

    Recount, recheck or restart? Here it's restart. After every deletion the scan goes back to index 0 and reads the same unmatched openers again. In the table above, almost every pair check is a repeat: 130,305 of 131,328 at n = 1,024.

    So don't go back. Keep the openers you've walked past and haven't matched yet. When a pair is deleted, the character just left of the cursor is the newest of them, and it's the only one you need to look at next.

    A closer arrives. Which of the waiting openers can it close?

    Only the newest. Every older opener has the newest one still open inside it, so closing an older one makes the pairs cross. In ( [ ), letting ) close ( would leave [ open inside the pair.

    So the waiting openers need three operations: add one at the end when an opener arrives, look at the newest when a closer arrives, and remove the newest when it matches. That's push, peek and pop. Each one is O(1).

    Cue → pattern

    “Closed in the correct order” means nesting: the bracket opened last must close first. Last in, first out is a stack.

    The plan card, and why it's correct

    Write this before any code. In a later re-solve you'll write it from a blank page.

    Problem
    20 · Valid Parentheses
    Pattern + cue
    Stack. “Closed in the correct order” means nesting: the last bracket opened must close first.
    State
    stack holds the openers of s[0..i) that are still waiting for their closer, oldest at the bottom.
    Invariant
    No closer in s[0..i) has failed, and stack is exactly what's left of s[0..i) after deleting every matched pair. 
    s[0..i)  read: its unmatched openers are on the stack | s[i..n)  not read yet

    not stack. With nothing left to read, the stack holds every opener that never closed.
    Complexity

    The argument, in four parts

    Initialization

    Nothing has been read and the stack is empty, so the invariant holds before the first iteration.

    Maintenance

    An opener can't be matched by anything already read, so it becomes the newest waiting opener: push. A closer can only close the newest waiting opener, because closing an older one would leave the newest open inside the pair. If the top matches, pop, and the invariant holds again. If the stack is empty or the top is another type, no later characters can repair s[0..i], so returning False right away is correct.

    Termination

    The loop reads each character once, so it ends. At that point the stack holds every opener that never closed, so the string is valid exactly when the stack is empty.

    Cost

    Chapter 3's three moves. Runs: line 4 runs n + 1 times, and every other line runs at most once per character. The lab's left column shows the exact counts. Cost: every line is O(1). Biggest term: n + 1, so O(n) time. The stack never holds more than n openers, so O(n) space.

    From plan card to code

    Write the subgoals as comments first. Each comment becomes one or two lines of Python.

    Subgoals
    # 1. map each closer to the opener it closes
# 2. scan s from left to right
#      opener: push it, it waits for its closer
#      closer: nothing waiting, or the top is another type -> invalid
#              otherwise pop, that pair is done
# 3. valid iff nothing is still waiting
    Python
    def is_valid(s):
    match = {")": "(", "]": "[", "}": "{"}  # closer -> opener
    stack = []                              # openers still waiting
    for ch in s:
        if ch in match:                     # ch is a closer
            if not stack or stack[-1] != match[ch]:
                return False                # none open, or wrong type
            stack.pop()                     # closes the newest opener
        else:
            stack.append(ch)                # an opener waits
    return not stack                        # valid iff none waits

    Another way to write it: push the closer you're waiting for same O(n), one dict lookup fewer 
    def is_valid_v2(s):
    want = {"(": ")", "[": "]", "{": "}"}   # opener -> the closer it needs
    stack = []                              # closers we still owe
    for ch in s:
        if ch in want:
            stack.append(want[ch])
        elif not stack or stack.pop() != ch:
            return False
    return not stack

    It returns the same answer as is_valid on every string checked for this page. stack.pop() != ch pops and compares in one step; not stack or guards the empty case first.

    An odd-length string can't be valid, so if len(s) % 2: return False is a fine first line. It doesn't change the Big-O.

    Lesson in one line: keep what's waiting on a stack when the newest waiting thing must be resolved first.

    Which end is the top?

    The end. One push plus one pop, measured on lists of growing size:

    items in the listappend + pop() (end)insert(0, x) + pop(0) (front)deque append + pop
    1,00016 ns279 ns20 ns
    10,00017 ns2.8 µs20 ns
    100,00017 ns34 µs20 ns
    1,000,00017 ns347 µs20 ns

    append and pop() cost the same at any size. insert(0, x) and pop(0) shift every element, so they grow with the list. collections.deque is fast at both ends and works as a stack too. queue.LifoQueue takes a lock on every call (about 1.1 µs per push and pop); it's meant for sharing between threads, so leave it out of interviews.

    Why append is O(1) on average

    When a list runs out of room, CPython reserves spare slots. Measured with sys.getsizeof:

    length after the append1591725334153
    slots reserved48162432405264

    The gaps between resizes grow with the list, so a million appends caused only 86 resizes. A few appends are slow and the rest are cheap: O(1) amortized.

    The empty-stack crash, and the guard that prevents it

    • [].pop() raises IndexError: pop from empty list
    • [][-1] raises IndexError: list index out of range
    • deque().pop() raises IndexError: pop from an empty deque

    So check for empty before you peek or pop: if not stack or stack[-1] != match[ch]:. or stops at the first true side, so on an empty stack the peek never runs. Swap the two sides and it crashes:

    if stack[-1] != match[ch] or not stack:   # sides swapped
    with stack = [] → IndexError: list index out of range

    A Stack class, for machine-coding rounds

    In an algorithm round, use a bare list. In a design round you may be asked for a class with a clear interface and clear errors. Keep it this small:

    class Stack:
    """LIFO stack on a list. The end of the list is the top."""

    def __init__(self):
        self._items = []

    def push(self, item):
        self._items.append(item)

    def pop(self):
        if not self._items:
            raise IndexError("pop from empty stack")
        return self._items.pop()

    def peek(self):
        if not self._items:
            raise IndexError("peek at empty stack")
        return self._items[-1]

    def __len__(self):            # len(s); `if s:` uses it too
        return len(self._items)

    def __repr__(self):
        return f"Stack({self._items!r})"

    Asteroid Collision

    LeetCode 735mediumFamily 1 · matching

    Each number is an asteroid in a row. Its size is the absolute value and its sign is its direction: positive flies right, negative flies left, all at the same speed. A right-mover and a left-mover that comes after it will collide. The smaller one explodes, and equal sizes both explode. Asteroids flying the same way never meet. Return the survivors, left to right.

    Understand
    [5, 10, -5] → [5, 10] · [8, -8] → [] · [-2, -1, 1, 2] → unchanged, because they fly apart.
    Brute force
    Find a right-mover directly followed by a left-mover, settle that collision, and rescan from the left. Up to n collisions, each after an O(n) scan: O(n²).
    Repeated work
    Every rescan re-reads survivors that can never collide with each other again.
    What waits
    The survivors so far, left to right. Only the newest right-mover, the top, can be hit next.
    Invariant
    Nothing inside the stack can collide: it always reads as left-movers, then right-movers.
    Resolve
    A left-mover hits the top while the top flies right. The smaller explodes. Repeat while the left-mover survives; if nothing is left in its way, it parks.
    Cost
    Line 5, the while check, decides it: it runs once per asteroid plus once per pass. Every pass destroys at least one asteroid, and none explodes twice, so there are at most n passes and line 5 runs at most 2n times. O(n) time, O(n) space.
    The brute force in Python. The lab was checked against it.
    def asteroid_collision_brute(asteroids):
    a = list(asteroids)
    while True:                     # one pass per collision
        for j in range(len(a) - 1):
            if a[j] > 0 > a[j + 1]:     # a head-on pair
                if a[j] > -a[j + 1]:
                    del a[j + 1]
                elif a[j] < -a[j + 1]:
                    del a[j]
                else:
                    del a[j:j + 2]
                break                   # rescan from the left
        else:
            return a
    • Chain reaction: one left-mover pops two right-movers in a single arrival. The total stays O(n) because each asteroid can explode only once. Chapter 10 counts it.
    • Moving apart: a left-mover on the stack is safe for good. Everything to its left also flies left, and anything that arrives later is to its right.
    • This is Valid Parentheses with sizes. A right-mover is an opener, a left-mover is a closer, and a collision is a match that may leave the closer still flying.

    Decode String

    LeetCode 394mediumFamily 2 · evaluating

    An encoded string uses k[text] to mean text repeated k times, and brackets can nest. Return the decoded string. The input is always well formed, every k is a positive whole number written right before its [, and the letters are lowercase.

    Understand
    3[a]2[bc] → aaabcbc · 3[a2[c]] → accaccacc, inner bracket first · 2[x10[y]]: a count can have two digits.
    Brute force
    Find an innermost k[…], one with only letters inside, replace it with its expansion, and rescan from the start until no [ is left.
    Repeated work
    Every expansion rescans and recopies the whole string, including everything outside the bracket it touched.
    What waits
    For each open bracket, its count and the text before it, saved when its [ was read. cur is the text of the innermost open bracket.
    Invariant
    If every open bracket closed right now, you'd get exactly the decoded prefix: fold the stack over cur.
    Resolve
    ] pops the newest bracket's (count, text before): cur = text before + cur * count.
    Cost
    Every line runs at most n + 1 times, but line 12 copies the string it builds, prev included. So the time is the runs plus the characters copied, which can be far more than n; chapter 10 counts them. The output alone can be exponentially long: 2[2[2[a]]] doubles at every level.
    The brute force in Python. The lab was checked against it.
    import re

def decode_string_brute(s):
    innermost = re.compile(r"(\d+)\[([a-z]*)\]")
    while "[" in s:                 # expand one innermost k[...]
        s = innermost.sub(lambda m: m[2] * int(m[1]), s, count=1)
    return s
    • Each [ saves the outer context and starts fresh, and each ] restores it. A function call does the same thing, which is why this problem also has a recursive solution.
    • Two-digit count: k = k * 10 + digit builds 10 from the 1 and then the 0.
    • The wrong options at each ] are real bugs: forgetting the saved text, repeating the saved text too, and forgetting to repeat.

    Next Greater Element I

    LeetCode 496easyFamily 4 · monotonic

    nums1 is a subset of nums2, and all values are distinct. For each value in nums1, find the first value to its right in nums2 that is bigger, or -1 if there is none.

    Understand
    nums1 = [4, 1, 2], nums2 = [1, 3, 4, 2] → [-1, 3, -1]. Nothing after 4 is bigger, and 2 is last.
    Brute force
    For each query, find it in nums2 and scan right: O(m·n). A falling input makes every scan run to the end.
    Repeated work
    The scans re-read the same stretch of nums2 over and over. Scan once instead, and let each value wait until something bigger shows up.
    What waits
    Values that haven't met a bigger value yet. From bottom to top they strictly decrease, since a bigger later value would already have popped a smaller one.
    Invariant
    The stack decreases, and every popped value has its final answer: the value that popped it.
    Resolve
    x pops every waiting value smaller than itself and becomes their answer, then waits too. Because the stack decreases, it stops at the first top bigger than x.
    Cost
    Line 5, the while check, decides it: it runs once per value plus once per pass. Every pass pops a value that was pushed once, so there are at most n passes and line 5 runs at most 2n times, however many one arrival pops. O(n + m) time, O(n) space.
    The brute force in Python. The lab was checked against it.
    def next_greater_element_brute(nums1, nums2):
    out = []
    for v in nums1:
        j = nums2.index(v)          # find v, then scan right
        while j < len(nums2) and nums2[j] <= v:
            j += 1
        out.append(nums2[j] if j < len(nums2) else -1)
    return out
    The coins

    Every value arrives with two coins. Its push spends one. Its pop, whenever it comes, spends the other, so an arrival that pops three values spends three coins saved earlier. Coins spent = pushes + pops = n + pops, which is exactly line 5's count, and it can't pass 2n.

    • Three pops at once: 5 pops 1, 3 and 4, then stops at 7. The waiting bars always form a staircase going down.
    • Falling: nothing is ever popped. Every value waits to the end, and its answer is -1.
    • The dictionary nxt is only there because the queries in nums1 name values. The stack work is the same without it.

    Binary Tree Inorder Traversal

    LeetCode 94easyFamily 5 · depth first

    Return a binary tree's values in inorder: the left subtree, then the node, then the right subtree. Do it with a loop and your own stack, without recursion. Trees are given the LeetCode way, level by level, with null for a missing child.

    Understand
    [1, null, 2, 3] → [1, 3, 2] · a binary search tree comes out sorted · an empty tree gives [].
    Recursive version
    Three lines and correct, but every level of the tree is a Python call. On a 2,000-node chain of left children it raised RecursionError, “maximum recursion depth exceeded” (the limit is 1000). The loop below handled the same tree.
    What waits
    Nodes whose left subtree you're still exploring. Each one gets visited once its left side is done.
    Invariant
    out, then the subtree under node, then each waiting node followed by its right subtree, newest first, is exactly the full inorder.
    Resolve
    When node is None, pop the newest waiting node, visit it, and go to its right child.
    Cost
    Line 5, the inner while, decides it: exactly 2n runs. It's true once per push and false once per pop, and each node is pushed and popped once. O(n) time. The stack holds one path down the tree at most, so O(h) space for a tree of height h.
    The recursive version and the TreeNode class
    class TreeNode:
    def __init__(self, val=0, left=None, right=None):
        self.val, self.left, self.right = val, left, right
    def inorder_rec(root):
    if root is None:
        return []
    return inorder_rec(root.left) + [root.val] + inorder_rec(root.right)
    • Each node sits at the x-position of its place in the inorder, so out fills in from left to right across the drawing.
    • Left chain pushes all five nodes before the first visit: the stack grows as tall as the tree.
    • The recursive version keeps the same waiting nodes on Python's call stack. Your own stack holds them without the depth limit.
    Chapter 10 · The math

    What makes a stack solution complete and efficient

    You've now seen five stack solutions. They share one template, and five rules decide whether a solution built on it is correct and O(n). Check them on your plan card before you write any code.

    The template · pseudocode
    stack = []                          # what waits (rule 1)
for x in items:
    while stack and resolves(x, stack[-1]):     # at most n passes in all (5)
        settle(stack.pop(), x)          # newest first, settled for good (2, 3)
    if hopeless(x, stack):              # only if no later item can fix it (3)
        return FAIL
    if waits(x):
        stack.append(x)
return finish(stack)                    # what leftovers mean (4)

    Rule 2 as a picture: a stack's arcs nest, a queue's cross

    Draw an arc from each opener to the closer that resolves it. A stack always takes the newest waiting opener, so any two of its arcs nest or sit side by side, and never cross. A queue always takes the oldest, so its arcs never nest.

    A queue pairs each ) with the oldest ( still waiting. On ((())), will the queue's arcs cross?

    Why a stack's arcs can't cross. Suppose two pairs (a, b) and (c, d) crossed, with a < c < b < d. When the closer at b arrived, the opener at c was still waiting, since it closes later at d, and it's newer than a. A stack would have paired b with c or something newer, never with a. Checked on all 2,056 balanced strings of ( and ) up to length 16: stack arcs never cross and queue arcs never nest. The two pairings differ on 2,047 of them and agree only on strings like ()()() with no nesting at all.

    The test for a stack

    If the things that resolve each other form arcs that nest or sit side by side, use a stack. If the first one in is the first one resolved, the arcs cross, and you want a queue.

    Rule 3, proved: why returning False early is safe

    Go back to the brute force from chapter 3, which deletes neighbouring matched pairs. When is_valid fails at a closer, that closer has nothing to its left after the deletions, or it has an opener of another type there. Later characters go on the right, so that left neighbour never changes. A pair is deleted only when an opener sits directly left of its own closer, so this closer can never be deleted, and no ending can make the string valid. In the other direction, the five implementations in the footer agreed on every string up to length 7, so the early return never rejected a valid string there.

    Rule 5, derived: count runs, not loops

    A while inside a for looks like O(n²). Don't multiply the loop sizes; use chapter 3's three moves. Every line in these solutions costs O(1), so the line that runs most often decides the Big-O. In a stack loop that's the while check, and one identity counts it:

    while checks = passes + entries   # each pass follows a true check,
                                  # and each entry ends with one false check
entries      = n                  # the loop is entered once per item
passes       ≤ n                  # each pass uses up something an item has once
while checks ≤ 2n

    What a pass uses up depends on the problem. In Next Greater Element it's a pop, and each value is pushed once. In Asteroid Collision it's an asteroid: every pass destroys the top, the arrival or both, and nothing explodes twice. In Inorder it's a push, one per node. One arrival can take many passes, but all of them together can't take more than n.

    Next Greater Element on Falling, then one giant: 999, 998, …, 1, then 1,000. The last value pops all 999 others in one arrival. Over the whole run, how many times does line 5, the while check, run?

    How often each line ran on one input with n = 1,000, counted by Python's tracer. The formula beside each line predicts that count: plain means exactly, ≤ means at most. The bar runs from 0 to 2n.

    When one run isn't O(1): Decode String

    Decode String has no inner loop, and no line runs more than n + 1 times (checked on 2,302 encodings). Here the second move matters. Line 12, cur = prev + cur * count, builds a new string, and building one costs a step per character copied.

    On 3[ab] repeated 200 times (n = 1,000), every ] copies everything decoded so far: 120,600 characters for an output of 1,200. With 400 groups the copying grew ×3.99, so it's Θ(n²) even though no line runs more than n + 1 times. Growing prev in place as a list writes 1,200 characters, one per output character.

    The list version
    def decode_string_list(s):
    stack = []                  # (count, pieces before) per open [
    cur, k = [], 0
    for ch in s:
        if ch.isdigit():
            k = k * 10 + int(ch)
        elif ch == "[":
            stack.append((k, cur))
            cur, k = [], 0
        elif ch == "]":
            count, prev = stack.pop()
            prev.extend(cur * count)    # grow prev in place
            cur = prev
        else:
            cur.append(ch)
    return "".join(cur)

    It returned the same string as decode_string and the brute force on all 2,302 encodings.

    Lower bounds: why O(n) time and a stack are the best you can do

    Time. Change any one character of a valid string and it becomes invalid. That was checked on all 11,497 valid strings up to length 10, 560,100 single-character changes. So an algorithm that skips a character can't tell those two strings apart. Every correct algorithm reads all n characters, and O(n) time is optimal.

    Memory. Take two different strings of openers, u and v, and append the closers of u in reverse. u becomes valid and v doesn't. So a checker that reads the string once must be holding different information after u than after v. After k openers there are 3ᵏ possible strings, so it needs at least log₂(3ᵏ) ≈ 1.58·k bits. That information is exactly what the stack holds: the order of the waiting openers.

    depth = 0                       # openers still waiting
    for ch in s:

    Reach for a stack when the state you must keep is the order of what's waiting, and you only ever touch the newest end of it.
