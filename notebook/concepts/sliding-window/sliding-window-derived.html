Chapter 1 · Brute force

Put every window on the (i, j) grid

Minimum Window Substring (LeetCode 76). Given strings s and t, return the shortest substring of s that contains every character of t, duplicates included, or "" if there is none. For s = "ADOBECODEBANC" and t = "ABC" the answer is "BANC".

A substring is fixed by its start i and its end j, with i ≤ j. Put i down the rows and j across the columns. Each cell on or above the diagonal is one substring, n(n+1)/2 of them in total. Any algorithm for this problem is a plan for which cells to look at.

The brute force below goes row by row. Each row starts fresh at j = i and grows the window one letter at a time until it contains all of t. Press Step and watch the run counts next to each line of code.

Python · brute forceruns · line · code · formula

What to notice

  • Each row stops at its first valid cell (the break). From the same start, a longer window can't be shorter, so the rest of that row can't win.
  • Each row throws its counts away and starts again at j = i. That's the expensive habit to watch.
  • Tick Show valid windows. The green cells form a staircase: each row's green part starts at, or to the right of, where the row above starts. Chapter 4 proves this always happens, and it's the whole trick.
Chapter 2 · Count

Count the line runs, read off the Big-O

Give each line a cost cₖ and count how many times it runs. This is how CLRS analyses insertion sort in §2.2. Here n = len(s), m = len(t), k is the number of distinct letters in t, and two counts depend on the input:

  • R: cells the brute force checks (inner-loop iterations).
  • V: rows that find a valid window and break (at most n).

A loop header runs once more than its body when the loop ends normally: the last check finds nothing left and exits. After a break there's no extra check. Python's own line tracer counts it this way, and the lab's numbers match it exactly.

Add it up

T = c₁·m + c₂ + c₃(n + 1) + c₄·n + c₅(R + n − V)
    + (c₆ + k·c₇)·R + (c₈ + c₉ + c₁₀)·V + c₁₁ + c₁₂·n

Worst case. No window is valid (try the “No answer” preset). Every row runs to the end, so V = 0 and R = n + (n−1) + … + 1 = n(n+1)/2:

T(n) = ½(c₅ + c₆ + k·c₇)·n²  +  (terms in n)  +  c₁·m  +  const
     = Θ(k·n² + m)

Best case. Every row is valid at its first cell (t = "A", s = "AAAA…"), so R = V = n and T = Θ(n + m). Interviews mean the worst case unless they say otherwise.

Shortcut

Drop the constants and every term that grows slower than the biggest one. In practice you only need the innermost line: how many times does it run, and what does one run cost? Here that's n²/2 runs × k comparisons.

O is an upper bound (grows no faster than), Ω a lower bound (grows at least as fast as), Θ is both at once. People usually say O when they mean the tight worst case.

The sliding window, counted the same way

Let S be the number of times l moves. The six lines in the while body run S times in total, and the while check runs n + S times: once after every shrink, plus one failing check for each r. l only moves forward and can't pass n, so S ≤ n:

T(n) = a·n + b·S + c₁·m + const  ≤  (a + b)·n + c₁·m  =  Θ(n + m)
Watch out

A loop inside a loop isn't automatically n². Count how many times the inner body can run in total, not per outer iteration. That's amortized analysis by the aggregate method.

Run both on bigger inputs

Thirteen letters hide the gap. Random text has short valid windows, so the brute force's break fires early and it looks fine. Text with no answer is its worst case.

Chapter 3 · Find the repeated work

Recount, recheck, restart

Most slow brute forces repeat work in one of three ways. Name the one you see and you know what to fix. The first two fixes make each cell cheaper. The third checks fewer cells, and that's where the big win is.

Version 1RecountΘ(n³)

It builds Counter(s[i:j+1]) for every cell, and that costs the window's length. Summed over all windows, Σ L·(n − L + 1) = n(n+1)(n+2)/6.

Fix: s[i..j+1] is s[i..j] plus one letter. Keep the row's counter and add that one letter.


          

        

        

          
Version 2RecheckΘ(k·n²)

          

            
After adding one letter, only that letter's count changed, yet all() re-checks all k letters.

            
Fix: keep have, the number of letters that already have enough copies. Only the letter you just added can change status, and only at the moment its count reaches the requirement exactly. That's the trick from your earlier question.

            

          

        

        

          
Version 3RestartΘ(n²)

          

            
When a row ends, the next one resets to j = i + 1 and re-adds letters it has just counted. Those cells are also guaranteed to be invalid: s[i+1..j] sits inside s[i..j], which was invalid for every j before row i's first valid cell.

            
Fix: don't reset j. Remove s[i] from the counts and carry on from where j stopped.

            

          

        

        

          
Version 4Sliding windowΘ(n + m)

          

            
Both pointers only move forward. The walk checks each cell on the staircase edge once: at most 2n cells instead of n²/2.

            

          

        

      

      
Two kinds of speed-up
Versions 1–3 visit the same R cells and only make each one cheaper. Version 4 changes which cells you visit. The biggest wins in DSA usually come from the second kind: proving that a cell can't be the answer, so you never look at it.

    

  


  
  

    

      
Chapter 4 · The window
Why it's a sliding window, and why it's correct

      
The staircase

      
For each start i, let f(i) be the first end j where s[i..j] is valid, or ∞ if there is none.

      
Lemma
f(i) ≤ f(i + 1). If s[i+1..j] contains all of t, so does s[i..j], because it contains s[i+1..j]. So row i turns valid no later than row i + 1.

      
In the grid, row i is green from column f(i) onward, and that starting column never moves left as you go down. That's the staircase. The best cell of each row is the left edge of its green part, and that edge only moves right as you go down.

      
A path that only moves right (r += 1) or down (l += 1) can trace the edge: move right while the window is invalid, move down while it's valid. Each pointer moves at most n times, so the path checks at most 2n cells.

      


      
Why it's called a sliding window

      
The candidate is always the range s[l..r]. Both ends only move forward, so the range slides along s like a frame. You never rebuild it: adding s[r] on the right and removing s[l] on the left each cost O(1).


      
The argument, written out

      
This is the “argue it's complete” step of your routine. Say these four things and the solution is proven, not just tested.

      

        
Invariant
Every time the while condition is checked, window holds the letter counts of s[l..r], and have is the number of letters c in t with window[c] ≥ need[c]. It holds at the start (empty window, have = 0). Each add or remove changes one letter's count by one, and have changes exactly when that letter crosses its requirement.

        
Sound
A window is recorded only inside while have == required, so by the invariant every recorded window is valid.

        
Complete
Let s[a..b] be a shortest valid window. l can only move past a by first recording a valid window s[a..r′], and r′ < b would be shorter than the shortest, which is impossible. So when r reaches b, l ≤ a. Every s[l′..b] with l ≤ l′ ≤ a contains s[a..b], so it's valid, and the loop keeps shrinking until it records s[a..b].

        
Fast
Each check comes right after r or l moves forward. Each moves at most n times, so there are at most 2n checks.

Chapter 5 · When it applies
Three conditions, and what breaks without them

      
    
        
  1. The answer is one contiguous range. A subarray or substring, or a pair of indices where only the range between them matters.
    2. 
        
  2. Validity is monotone. Either growing a valid window keeps it valid (shortest-window problems), or shrinking one keeps it valid (longest-window problems). This is what makes the staircase, and what lets l move only forward. Fixed-size windows don't need it: they walk one diagonal and check every cell on it.
    3. 
        
  3. The state updates cheaply. Adding the element that enters on the right, removing the one that leaves on the left, and checking validity each cost O(1) or amortized O(1). Sums, counts and sets are easy. A maximum isn't, because you can't undo the max when its element leaves. That's why Sliding Window Maximum needs a deque.
    4. 
      

      
Condition 2 is the one that fails quietly. Below is one rule, shortest subarray with sum ≥ 7, on two arrays. On the left every number is positive (this is LeetCode 209). On the right there's a −2.

    

    

      

        

        

      

    

    

      
With the −2, removing an element can raise the sum. On the right grid, row 2 turns valid at column 3 but row 1 only at column 4, so the staircase steps the wrong way. The walk passes over cell (2, 3), which is the true answer [5, 2], and returns 3 instead of 2.

      
When values can be negative, use a different tool. Subarray Sum Equals K (560) uses prefix sums with a hashmap. Shortest Subarray with Sum at Least K (862) uses prefix sums with a monotonic deque.

    

  


  
  

    

      
Chapter 6 · Templates
Three walks across the grid, three templates

      
Every sliding-window problem walks the grid in one of these ways. Learn the walk first; the code follows from it.

    

    

      

        

          
Fixed size k

          
Walks one diagonal of the grid: every window of length k, once. No monotonicity needed.

          

          
Permutation in String · Sliding Window Maximum · Find All Anagrams · Contains Duplicate II

        

        

          
Longest valid

          
Validity survives shrinking. Shrink while invalid, then record: [l..r] is the longest valid window ending at r.

          

          
Longest Substring Without Repeating Characters · Longest Repeating Character Replacement · Max Consecutive Ones III

        

        

          
Shortest valid

          
Validity survives growing. While valid, record and shrink: each pass tries a shorter window.

          

          
Minimum Window Substring · Minimum Size Subarray Sum

        

      

    

    

      
A fourth shape: dominance. Best Time to Buy and Sell Stock and Sliding Window Maximum use a different argument: this element can never be the answer again, so drop it. In the stock problem l jumps straight to a cheaper day. In the maximum problem, smaller elements are popped off a deque. Pointers still only move forward, so the cost stays linear.

      
Where people slip
        
    
          
  • Recording in the wrong place. Longest records after the while; shortest records inside it.
    • 
          
  • Window length off by one. It's r - l + 1.
    • 
          
  • Using a set when duplicates matter. t = "AAB" needs two A's.
    • 
          
  • Using len(counts) as “number of distinct values” without deleting keys whose count dropped to 0.
    • 
          
  • Shrinking with if when one removal might not be enough. Use while unless you've proven one step always suffices.

Best Time to Buy and Sell Stock
Easy · LeetCode 121

        
prices[i] is the price on day i. Buy on one day, sell on a later day, and return the largest profit, or 0 if you can't make any.

        
Shape: dominanceState: cheapest day so farTime: Θ(n)

        

        

          
1Brute force & count
Rows are buy days, columns sell days. Try every cell with i < j: n(n−1)/2 cells, Θ(n²).

          
2Repeated work
For each sell day, the brute force rescans every earlier day looking for the cheapest one. That minimum only changes by one comparison per day.

          
3Classify
Dominance, not validity. l is the cheapest day so far and r is the sell day. l never moves back, but it can jump several rows at once.

          
4State
The index l and the best profit so far. Nothing else.

          
5Argue
Why the jump is safe. If prices[r] < prices[l], then for every later sell day, buying on day r is cheaper and still in time. Every row from l to r − 1 is beaten by row r from now on.
Invariant. Before handling day r, prices[l] is the minimum of prices[0..r−1], and best is the best profit from any sale before day r.

Longest Substring Without Repeating Characters
Medium · LeetCode 3

        
Return the length of the longest substring of s in which no character appears twice.

        
Shape: longest validState: set of letters in the windowTime: Θ(n)

        

        

          
1Brute force & count
Check every substring for repeats from scratch: Θ(n³). Grow a set along each row and stop at the first repeat: Θ(n²).

          
2Repeated work
Restart. When a repeat shows up, the next row starts over at i + 1 and re-adds letters it already knows are distinct.

          
3Classify
Longest valid window. Valid means no repeats, and removing letters can't create a repeat, so validity survives shrinking.

          
4State
A set of the letters in s[l..r]. (Or a map from letter to its last index, for the faster variant below.)

          
5Argue
Monotone. Let g(r) be the leftmost start that makes s[g..r] valid. If s[l..r+1] is valid, so is s[l..r], so g(r) ≤ g(r + 1). The best start only moves right, so l never needs to go back.
Invariant. After the while loop, seen holds exactly the letters of s[l..r], which has no repeats and is the longest such window ending at r.

Longest Repeating Character Replacement
Medium · LeetCode 424

The famous trick: never lower maxf optional, Θ(n)

              
Keep maxf, the largest count seen so far, never decrease it, and shrink with if instead of while. The window then never shrinks. It slides at its best length until a bigger maxf lets it grow, and the answer is its final length.

              
Why it's still correct. The answer can grow by at most 1 per step, and only if the window of length best + 1 ending at r is valid. maxf is never below the true top count of the current window, so a real growth is never missed. A stale maxf can't fake a growth either: once the window fails to grow it slides at a fixed length and can't grow again until maxf rises; while it keeps growing, its left edge stays put, so it still contains the maxf copies counted earlier.

              
In an interview, code the clear version and mention this as a follow-up.

              

          
8Final cost
Θ(26·n) = Θ(n) time, O(26) space.

Sliding Window Maximum
Hard · LeetCode 239

        
For every window of size k in nums, report its maximum.

        
Shape: fixed size + dominanceState: monotonic deque of indicesTime: Θ(n)

        

        

          
1Brute force & count
Take the max of each window: (n − k + 1) windows × k = Θ(n·k). A heap with lazy deletion gets Θ(n log n).

          
2Repeated work
Recount. Each window re-compares k − 1 numbers the previous window already compared.

          
3Classify
Fixed size, but it fails condition 3: you can't undo a max when its element leaves. You need a structure that keeps the max ready while elements enter and leave.

          
4State
A deque of indices whose values never increase from front to back. The front is the window's max.

          
5Argue
Why popping is safe (dominance). If i < j and nums[i] < nums[j], index i can never be a max again: every future window that contains i also contains j, which is bigger and leaves later.
Invariant. The deque holds, in index order, exactly the indices of the current window that could still become a max, and their values never increase from front to back.

7Implement & test
Edge cases: k = 1 returns nums; k = len(nums) returns one value; repeated values; negative numbers.

8Final cost
Θ(n) time: each index is pushed once and popped at most once (amortized again). O(k) space.

monotone  containing t survives growing
record    inside the while, before shrinking
cost      Θ(n + m) time, O(k) space

        

        
Software-design habit
Notice what you did in every problem: chose a representation (counts, a set, a deque) that makes the operations you need cheap, then stated an invariant that the representation keeps. That's the same move you make when designing a class or a service: pick the data that makes the common operations cheap, and write down what must always be true about it.
