Spot the proof before the template.

Binary search works when a test lets you discard a whole side of an ordered search space. The candidates might be indices, versions, speeds, capacities, distances or times.

Four questions to ask yourself

  1. What am I searching over? Name the candidate and its bounds.
  2. Can I test one candidate? Turn “find the minimum” into “would this value work?”
  3. What happens on either side? Prove which answers cannot change back.
  4. What boundary do I want? First true, last true, or a different elimination proof?

The common boundary pattern

False False … False | True True … True

A yes/no test is a predicate. If its answer changes at most once in this order, it is monotone. Search for the first true; do not enumerate every candidate.

“Sorted”, “first/last”, “minimum feasible” and “maximum possible” are useful cues. The cue starts the investigation. The proof justifies the move.

One boundary template, several interpretations
def first_true(lo, hi, works):
    # candidates are integers in [lo, hi)
    while lo < hi:
        mid = (lo + hi) // 2
        if works(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo

Before lo: false. From hi onward within the original domain: true. Unknown candidates: [lo, hi). The first-true boundary lies in [lo, hi].

If the return equals the original exclusive upper bound, no candidate worked. If all candidates work, it returns the original lower bound.

For true → false, search for the first false with not works(x), then subtract one. If that goes below the lower bound, there was no true candidate.

Related patterns that need their own proof

Rotated sorted arrays: determine which half is sorted, then whether that half can contain the target. Raw a[i] ≥ target need not be monotone. Duplicates can make the useful half ambiguous and force linear worst-case work. Where each = comes from.

Find any peak: comparing adjacent values can prove a peak exists on one side (under the problem’s boundary and unequal-neighbor assumptions). The array need not be globally monotone. This is an elimination argument, not the first-true template unchanged.

Continuous answers: a monotone feasibility test can narrow a real interval, but integer mid + 1 does not apply. Stop at a justified tolerance or iteration count.

Costs matter: fast random access or an efficient feasibility check matters. A linked list’s middle is expensive to reach; sorting once for one lookup can cost more than simply scanning.

Start with an array boundary.

Given sorted values, return the first index equal to the target, or −1 if it is absent. First find the first value ≥ target; then check equality.

[0, lo) → smaller than target[lo, hi) → unknown[hi, n) → at least target

The parts

lo starts the unknown range. hi ends it, exclusively. mid = (lo + hi) // 2 picks an index inside it.

The boundary answer lies in [lo, hi], including hi. The unknown elements occupy [lo, hi). These are different claims.

Your plan card

Start: lo = 0, hi = n. All elements are unknown.
Continue: while lo < hi.
Move: smaller → lo = mid + 1; otherwise → hi = mid.
Stop: lo == hi. Check whether that index exists and equals the target.

Why each move is safe

If nums[mid] < target, sorted order proves every value through mid is too small. Skip mid as well: lo = mid + 1.

Otherwise, mid and every element to its right are at least the target. Mid might be the first such index, so keep it as the boundary: hi = mid. Do not use hi = mid − 1 with this half-open template.

Progress: hi − lo strictly shrinks. Setting lo = mid can get stuck when only one element remains.

Relies on: sorted, ascending input makes nums[i] >= target change only from false to true. Unsorted input breaks the proof; use a scan, or sort if changing the original index order is acceptable.

Search possible answers, not the input.

Jobs have sizes [9, 3, 7]. Each job gets whole time slots of its own. At speed k, a job needs ceil(size / k) slots. Find the minimum integer speed that finishes all jobs within 7 slots.

Build the decision question

Candidate: speed k, from 1 through 9.
Test: sum(ceil(job / k)) ≤ 7.
Proof: increasing k cannot increase any job’s time. Once a speed works, every faster speed works.
Boundary: the first feasible speed.

Why an unsorted input is fine

The ordered space is speeds, not job positions. Reordering these jobs does not change the time sum. We never sort the input.

With m positive jobs, speed max(jobs) takes exactly m slots. If the deadline is less than m, no speed can work. The template returns its upper sentinel; the wrapper converts that to None.

    Four questions before you write the loop

    1. Where can the answer be? If it can be “none of them” or one past the end (an insert position, no speed that works), start hi = len(nums): the range is [lo, hi). If it is always an element the loop reads, start hi = len(nums) - 1: the range is [lo, hi]. A loop that reads nums[hi] needs the second.
    2. When mid passes, do I know it is the answer?
      Yes, on the spot (an exact match): return it, and every other branch drops mid with mid ± 1. One unchecked element still needs its look, so while lo <= hi.
      Maybe, but not yet (the first ≥ target, the first bad version, a minimum, the slowest speed that works): keep mid with hi = mid, stop at one candidate with while lo < hi, and read the answer at lo after the loop.
    3. Where do equal values belong? Put the = on their side. First index ≥ target: an equal value is an answer, so go right only on nums[mid] < target. First index > target: an equal value is not, so go right on nums[mid] <= target. When equality can’t happen, the = changes nothing, but say why it can’t.
    4. Run the two-element test. Shrink to lo and lo + 1: floor mid is lo. Every branch must shrink the range. Then one element: does the loop look at it, or the code after the loop?

    Rotated arrays: where each = comes from

    Target (LC 33): your solve, line by line

    • while lo <= hi and mid ± 1. A match is confirmed on the spot, so this is the first template with a different way of picking the side.
    • nums[lo] <= nums[mid]. The = covers lo == mid, which floor mid produces on two elements. With <, Python returns −1 on [3, 1], target 1. With mid rounded up, lo == mid happens only on the last element, which the == line has just checked, so < passes there. The = follows from where mid can land.
    • nums[lo] <= target < nums[mid]. Inclusive at lo, strict at mid: the == line checked mid, but not lo. The right side mirrors it: nums[mid] < target <= nums[hi].
    • Is mid in both halves? Yes: [lo..mid] and [mid..hi] share it (your question q0007). That is harmless because the == line has already ruled mid out, and it is why both range tests are strict at mid.
    • Compare with the other end and the = moves. nums[mid] > nums[hi] also proves the left half sorted, since the drop is then on the right. Python passes it on every input.

    Show the reasoning (spoiler for LC 153)
    • No target, so nothing is confirmed on the spot. Mid may be the minimum, and you only know once everything else is ruled out. That is the “first that passes” template: while lo < hi, keep mid with hi = mid, answer nums[lo].
    • Compare with nums[hi]. If nums[mid] > nums[hi], the drop is right of mid, so the minimum is in (mid, hi]: lo = mid + 1. Otherwise nums[mid..hi] is sorted, so the minimum is mid or left of it: hi = mid.
    • Not nums[lo]. Seen from lo, a sorted range and a range whose drop is right of mid look the same. On [1, 3, 5], nums[mid] > nums[lo] sends the search right and Python returns 5.
    • > or >=? Both pass. With lo < hi, floor mid is below hi, and distinct values make nums[mid] == nums[hi] impossible. With duplicates (LC 154) it can happen and tells you nothing: drop one with hi -= 1, which makes the worst case O(n).
    • hi starts at len(nums) - 1 because the loop reads nums[hi] and an answer always exists.

    Count the work, then name it.

    Each iteration keeps at most half the unknown elements. For n ≥ 1, this loop uses at most floor(log₂ n) + 1 iterations. For array lookup, that is O(log n) time and O(1) extra space.

    These counts were measured by executing Python on sorted even values and every integer target from just below to just above each array. They count loop comparisons; the final equality check is separate. The explainer stores extra history, but the algorithm does not.

    Search over answers: if testing one candidate costs C and there are R candidate integers, budget O(C log R), plus setup. The speed example scans m jobs per test: O(m log M) time for M = max(jobs) ≥ 2, O(m) for M = 1, and O(1) auxiliary space. The midpoint loop alone is not the whole cost.

    Where it breaks.

    • Guard and update disagree. while lo <= hi with hi = mid never stops once lo == hi.
    • Floor mid with lo = mid. On two candidates mid is lo, so nothing moves. Round mid up, or rewrite as first fail minus one.
    • The last element never checked. while lo < hi with hi = len(nums) - 1 and a return on a match: [1], target 1 returns −1.
    • Returning on a match when you want the first occurrence. On [1, 2, 2, 2, 3], target 2, the exact-match loop returns 2; the first 2 is at index 1. Use first ≥ target.
    • The = on the wrong side. nums[mid] <= target finds the first index > target, not ≥.
    • Reading past the end. After a first-≥ loop, lo can be len(nums): check lo < len(nums) before nums[lo]. With hi = len(nums), never read nums[hi].
    • Rotated: < in the sorted-half test. [3, 1], target 1 returns −1.
    • Rotated: duplicates. When nums[lo] == nums[mid] == nums[hi] you can’t tell which half is sorted. Shrink by one; the worst case becomes O(n) (LC 81, 154).
    • Other languages. lo + hi can overflow a 32-bit int in Java or C++; write lo + (hi - lo) / 2. Python integers don’t overflow.

    Make the proof yours.

    For a first-true search, ordered candidates and a false-to-true predicate let one test classify a whole side. Everything before lo fails; everything from hi onward in the domain works. For minimum speed, increasing speed cannot increase completion time. Each update strictly shrinks hi − lo.
